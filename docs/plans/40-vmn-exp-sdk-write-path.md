### C1. A failed final state / final log upload is retried within the budget and warned about, never silent

P0 · M

**Problem.** Verified by reading and by a probe. RunStatePublisher._upload lets an exception from the remote compare-and-save escape into Coalescing._loop, which logs at debug and moves on. Coalescing.close() returns True because the worker exited, so Run._close_writers reports nothing and no 'still uploading' warning fires; the remote keeps state=running and later reads stuck. The final log sync has the same shape: it is wrapped in quiet(_LOGGER) (debug only). A persistently failing heartbeat upload is also debug-only, but is repaired by the next beat (newest-wins), so only a one-time warning is owed there.

**Approach.**

Coalescing stays unchanged (shared with cli/supervisor.py and the sweep agent). (a) New SDK/core/final_retry.py (~50 lines; in core beside background.py and best_effort.py, so C15's supervisor imports it without importing the vmn_exp.sdk package): FinalRetry(attempt, wait, delays=(0.5,1,2,5)) - run(item) calls attempt(item) until it returns, the `wait(delay)` callable reports 'abandoned' (returns True), or delays are exhausted-and-repeating at the last value; remembers `error` and `landed`. `wait` is injected (Run passes a threading.Event().wait; tests pass a fake that records delays and returns False/True) - no real sleeping in tests, no hidden default. (b) state_publisher.py: gate-wrap the single attempt (self._attempt = gate.wrap(self._upload_once)), not the loop, so a fork is never held for the whole retry; _upload: non-final -> BestEffort(warn_first=True) around the attempt ('vmn: could not upload the state of run X: <exc>' once, then debug); final -> FinalRetry. close(timeout): joined = self._remote.close(timeout); set the abandon event; return joined and (final landed or superseded or no final submitted); expose `last_error`. (c) New SDK/sdk/log_sync.py (~50 lines) LogSync: owns the 'vmn-exp-sync' Coalescing now built inline in Run.__init__ (same gate wrapping per attempt); it receives the sync job as a callable defined in run.py, because tests patch `sync_to_remote` and `compact_by` on vmn_exp.sdk.run (test_sdk_detach.py:86, test_exp_push_metrics.py:90,131) and the patch must still apply; submit() periodic stays debug-only; submit(final=True) goes through FinalRetry; close(timeout) is False when the final sync did not land; `last_error`. (d) run.py _close_remote_writers: a writer returning False prints 'is still uploading' when it has no error, else 'vmn: the final <what> of run X was not uploaded: <exc>'. The recovery hint in that message is added by the items that make it true (C2: 'run `vmn-exp push`' for local-first; C13/C6: 'vmn-exp buffers ship' for direct-to-bucket) - C1 itself promises nothing it cannot keep. The two store kinds are told apart by one function next to `local_side` in storage/cached.py, `is_log_buffer(storage)` (a CachedSnapshotStorage whose local side is not a replica: `_local_is_replica`, False for the buffer at buffered.py:61); it is added with the first hint and C15 uses it too, so no caller reads the private attribute and no storage probe is added. finish()'s return value is unchanged.

### C2. `vmn-exp push` repairs a remote run_state.yml that never received the run's final state

The helper is reused by C13 and C6.

### C13. Direct-to-bucket mode: the buffer (the only local copy of the final state) is not removed until the remote holds the final state

P1 · M · depends on C2, C3

**Problem.** New, verified by reading and by a probe. For a BufferedRemoteStorage, split_storage returns the buffer's LocalSnapshotStorage as the inline side, so the final run_state.yml is written into the buffer dir and its remote copy is queued. The final log sync then runs on another worker: BufferedRemoteStorage.sync_log_to_remote sees nothing unshipped and the run finished locally, and rmtree's the buffer. If the state upload fails or is still retrying (finding 1), the final state now exists nowhere. Probe: remote save_file_if_match raising for the final state + one successful log sync => publisher.close() True, remote state `running`, tempdir empty. The exit flush (close()) removes the buffer the same way without looking at the state.

**Approach.**

buffered.py only (plus one small helper module if buffered.py would pass ~300 lines: SDK/storage/buffer_state.py). (1) The eager cleanup at sync_log_to_remote:192-198 additionally requires that the remote's run_state.yml is final (one remote read, evaluated only when the local state is finished and nothing is unshipped - i.e. once or twice per run end). When it is not, the storage stays in _PENDING so the exit flush decides. (2) _close(): for every record in the buffer whose local state is finished, call C2's publish_final_if_unfinished(remote, app, verstr, local_state) before deciding; a raise counts as 'did not ship' (-> _keep_buffer, with the existing warning extended to say the final state of <verstr> is in the kept dir); a refusal because the remote is already final (this or another attempt) counts as shipped. The exit flush therefore gives a lost final state one more attempt. (3) No change to the SDK: after C1 the publisher keeps retrying within the budget; this item only guarantees the local copy survives until someone succeeds.

### C3. An SDK run's direct-to-bucket ships run on its gated sync worker, not on the appending thread

P1 · S · depends on C1

**Problem.** Verified. BufferedRemoteStorage ships inside the append whenever the 5 s interval is due and on every first append (_ship_if_due -> sync_log_to_remote; append_metric_block -> sync_metrics_to_remote). In the SDK those appends run on the heartbeat thread (Run._beat -> _log_buffer.flush), on the 1 s flusher thread, and on the caller's thread once 1000 entries are pending (LogBuffer.append -> _flush_quietly), all under LogBuffer._write_lock. A hung store is bounded only by boto (10 s connect / 30 s read, 5 attempts): log_metric can stall for minutes, beats are delayed, and finish()/SIGTERM wait on _write_lock. This contradicts the design stated in state_publisher.py:4-9 and background.py:4-8.

**Approach.**

Keep the storage inline by default (one-shot CLI commands and the UI server want the write on the bucket before they return, and existing tests pin it). Add a per-run hand-off: buffered.py gains defer_ships(app, verstr, request) / undefer_ships(app, verstr) storing the callable in a dict that _start_buffer resets (a forked child never calls its parent's worker). _ship_if_due and append_metric_block: when due and a requester is registered for (app, verstr), mark the key unshipped, call request() (non-blocking) and return True; otherwise today's inline path, unchanged. sdk/run.py: Run._open does `defer = getattr(storage, 'defer_ships', None)` and registers `lambda: self._log_sync.submit()` (C1's LogSync; the job is the existing sync_to_remote, which ships logs and metrics); _close_remote_writers' finally and detach/release undefer. The work thus runs on the run's existing gated Coalescing worker: plan-30 fork pausing, the bounded close and C1's final retry all apply with no new thread and no storage-level at-fork hooks. After this, LogBuffer's eager flush and the heartbeat's flush are local disk appends in every mode vmn constructs. No clock injection is needed: due-ness logic is untouched.

### C15. `vmn-exp run`'s supervisor: the final state and final log upload are retried within one budget and reported, and no upload runs on the supervise loop

P1 · M · depends on C1, C3, C13 (C2 and C6 for the recovery hints)

**Problem.** New item (owner decision 2026-11-11), verified by reading at HEAD. After plan 38 A5 the supervisor is the only writer of an adopted run's state, so its upload gaps become the default path of `vmn-exp run` + `start_run()`. Four gaps. (a) Final log sync: `_sync_once` runs `sync_to_remote` under `supervision_guard()`, a warn-first BestEffort. A failing final sync is tried once; it is a warning only when no earlier periodic sync failed in this process, otherwise debug only, and the warning's wording is 'remote sync failed (...); supervision continues'. `BackgroundSync.final` warns only when the worker did not finish in time: a sync that raised returns normally and `_finish` goes on to log 'exited N in Ds'. (b) Final state: `_publish_final` tries three times with a real `time.sleep(1)`, each attempt bounded only by the backend's own timeouts, logs the exception at debug and warns 'could not record the final run state' with neither the reason nor a way to recover. (c) State writes on the supervise loop: every heartbeat calls `_publish` -> `save_run_state` -> `storage.save_file` on the loop. With a remote that holds the record that is an inline PUT. ### C6. `vmn-exp buffers list|ship`: ship kept or orphaned log buffers whose owner is gone, and their final state

P2 · M · depends on C5, C2, C13

**Problem.** Verified answer to the follow-up: a kept buffer dir cannot be pushed with `vmn-exp push` and nothing else ships it (the code's own warning says so). The buffer is not a replica: metadata with empty patches, this process's stream files, .ship state and run_state.yml (confirmed by listing a probe buffer) - no code patches, no store.yml; and push refuses a differing remote run_state.yml (C2). What is reusable is the storage's own ship path: it resumes past the bytes the remote holds under the record's cross-process ship lock, and a BufferedRemoteStorage treats every stream in its dir as its own, so reopening a kept dir ships exactly what is missing.

**Approach.**

The rule: a buffer is shipped only by a process that holds its owner lock. `buffers ship` takes C5's <root>/.buffer-owner.lock (non-blocking, through storage/buffer_owner.py) before it touches a buffer and holds it until it is done with that buffer. It gets the lock only when the owning process is gone or gave the buffer up (_keep_buffer releases it). A buffer whose lock cannot be taken belongs to a live owner: it is listed as live and never shipped, compacted or removed from outside. Two `buffers ship` runs exclude each other the same way.

(1) New SDK/core/buffer_recover.py (~120 lines, IO injected: list_dirs, read_marker, open_remote(marker), try_lock, remove_tree): kept_buffers(bases) -> [{root, pid, host, started_at, remote, runs, live}], where live is 'the lock could not be taken' (probed and released at once). ship_buffer(root, remote, try_lock) -> outcome: take the lock, or return 'live' without opening anything; open the dir with BufferedRemoteStorage.reopen(root, remote) (new classmethod: existing root, no fresh owner minted for existing stream files, never registered in _PENDING, takes no second owner lock); sync logs and metrics for every (app, verstr) in it; then C2's publish_final_if_unfinished for each record whose buffered state is final. The dir is removed when everything shipped; otherwise it stays and the lock is released. A SIGKILLed run's state is left alone (it reads stuck; the user ends it with `vmn-exp finish`): recovery never invents an exit code. A dir without a marker or without a lock file (a buffer kept by a release before C5, or a foreign dir) is listed as unknown and neither shipped nor removed: no lock proves its owner is gone. Where fcntl is missing no lock can be taken, so `ship` ships nothing and says so. (2) CLI packages/vmn-exp/src/vmn_exp/cli/buffers_cmd.py: `vmn-exp buffers list` (age, host, pid, live, store, runs, bytes; read-only, takes no repo lock) and `vmn-exp buffers ship [--store URI] [--keep]` (`--keep` leaves a fully shipped dir in place). `ship` prints one line per buffer (shipped, live: skipped, unknown: skipped, failed: <error>) and exits non-zero only when a buffer it locked could not be shipped; skipped buffers do not fail it. (3) The kept-buffer warning (C5) and C1's direct-to-bucket message end with 'ship it later with: vmn-exp buffers ship'. (4) The stream-owner invariant gains its one exception, in the same commit, in both places it is written - CLAUDE.md ('only a stream's owner appends/ships/compacts it') and docs/vmn-exp/experiments.md:1833 ('Only a stream's owner ships, compacts and pushes it'): 'The one exception is `vmn-exp buffers ship`: it ships a log buffer's streams after taking that buffer's owner lock, which it can only when the owning process is gone or has given the buffer up. **Approach.**

(1) New SDK/sdk/process_hooks.py (~50 lines): install_once(sys_module, atexit_module, finalize, note_uncaught) - idempotent per pid, chains the previous excepthook, registers the atexit finalizer. Run._open calls it (any thread) with the `sys` and `atexit` modules start_run chose (an entry point that may build real IO, plan 37 decision on CLAUDE.md). run.py drops the module-level `sys.excepthook = ...` and `atexit.register(...)`. (2) Exit order CHANGES and that is intended: registering at the first Run._open (after the storage - and so buffered/journal - was imported) makes the run finalizer run BEFORE buffered.close_all and journal._flush_all, which become the last safety net they were meant to be. This is a behaviour change, pinned by a test and given an upgrading.md row (plan 43 F9); it is not preserved behaviour. (3) SIGTERM: keep install_signal_handlers() at import (only the main thread may install a handler, and runs opened later from worker threads could not; pinned by test_sdk_sigterm.py:145); signals.install gains a has_work callable (context.open_runs non-empty); _handle with no work restores/chains at once without spawning a thread. (4) Docs: sdk.md 'Threads, forks' states exactly what import does (one chained SIGTERM handler, nothing else) and how to undo it.

### C10. State the durability contract: safe against process crash, not host crash (no fsync)

P3 · S

**Problem.** Verified. atomic_write is temp + rename with no fsync of the file or its directory; log/metric appends are plain write + close; grep finds no fsync anywhere under packages/vmn-exp-sdk/src or packages/vmn-exp/src. A record survives a process crash; a host crash or power loss can lose the last seconds of appended lines and, on filesystems without rename-replace auto-flush, leave a just-renamed run_state.yml or metadata.yml empty. No doc says so.

**Approach.**

Document, do not fsync. A 'Durability' subsection in docs/vmn-exp/experiments.md (storage section) and one sentence in sdk.md beside the log batching paragraph: local writes are atomic against readers and a process crash; they are not synced, so a host crash can lose what the OS had not written back and, rarely, leave a state file empty; the remote copy is the durable one - use a remote store or `vmn-exp push` for runs that must survive a host loss. One pinning test for the reader-side claim the doc makes.

**Tests first.**

- TESTS/test_experiment_writer_core.py::test_an_empty_run_state_file_reads_as_no_state (pins the documented behaviour through load_run_state and derive_status; a new test, expected to pass on arrival; if it fails that is a separate bug to report, not a reason to change the documented claim)

**Files.** `docs/vmn-exp/experiments.md`, `docs/vmn-exp/sdk.md`, `packages/vmn-exp/tests/test_experiment_writer_core.py`

**Risk.** None for code. fsync was decided against: it is slow on NFS/Lustre and network block devices - where training jobs write - and would have to reach every backend's save_file_if_match to cover only the final state.

**Owner decision (2026-11-11).** Document only. No fsync on the write path.

### C11. Document the per-process .rN listing and its existing escape hatches

P3 · S

**Problem.** Verified as described, and designed: a `.rN` claim with no in-process hint lists the code version's run names once (names only, scoped to the code version where the backend can), then claims upward from the hint for the rest of the process. For a fleet of single-run processes on one code version that is one listing per process, so total work grows quadratically. Two escape hatches already avoid it: a writer suffix (VMN_WRITER_ID lists only names under <code>.<suffix>) and an exact run_id (one exclusive create, no listing). The docs do not connect them to this cost.

**Approach.**

Docs only: in docs/vmn-exp/client-guide.md (Kubernetes git-free recipe) and docs/vmn-exp/experiments.md (run naming) add 'Many runs of one code version': each new process lists that code version's run names once to pick .rN; for fleets and sweeps of thousands of runs set VMN_WRITER_ID so each writer lists only its own names, or pass run_id for a listing-free exclusive create. No code change.

**Tests first.**

- none new - unchanged behaviour already pinned by TESTS/test_run_allocation_listing.py (test_a_writer_suffix_lists_only_names_under_code_dot_suffix :69, test_repeated_rn_allocations_in_one_process_list_once :97)

**Files.** `docs/vmn-exp/client-guide.md`, `docs/vmn-exp/experiments.md`

**Risk.** None. **Owner decision (2026-11-11).** Document only: for fleets, set VMN_WRITER_ID or pass an exact run_id. No change to .rN allocation.
